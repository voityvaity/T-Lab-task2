# Повторная проверка №2 — T-Lab 2026

**Дата:** 25 октября 2026 года. **Статус проверки:** анализ исходного кода, тестовых сценариев, публичной схемы Yambda, workflow и научных предпосылок. **Не** подтверждение реального обучения или зелёного CI.

## Проверенные факты

- В репозитории присутствуют независимые реализации модели GPT-2, обучаемых reward-head, двух методов RL (одношаговый REINFORCE и гипотетический пятишаговый rollout), popularity / лёгких sequential rules, reranking, offline-метрик и генератора отчёта.
- Yambda `flat/50m/listens.parquet` содержит `uid, item_id, timestamp, is_organic, played_ratio_pct, track_length_seconds`, `timestamp` — **пятисекундные bins** (документация: https://huggingface.co/datasets/yandex/yambda).
- Команда загрузки `hf download ... --repo-type dataset --revision ... --local-dir data` соответствует справочнику CLI Hugging Face (https://huggingface.co/docs/huggingface_hub/en/guides/cli).
- Временные границы рассчитываются глобально, пользователи выбираются по **train-only** истории, словарь строится только из train, а события одного пятисекундного интервала не добавляются в контекст друг друга.
- Реализация использует observer-only отклики; контрфактические оценки reward и пятишаговые гипотетические состояния нельзя считать наблюдаемыми реакциями.
- Прогоны в GitHub Actions разрешены исключительно вручную; перед обучением теперь запускаются проверка зависимостей, компиляция Python и pytest.

## Найденные и исправленные недочёты в этом аудите

1. **Неправильная обработка позиционных эмбеддингов GPT-2.** При левой PAD-подкладке раньше не передавались явные `position_ids`. Теперь real-token position считается по cumulative attention mask, в том числе внутри замороженного reward encoder. Добавлен отдельный тест.
2. **Завышение ранжирующих метрик из-за исключения OOV targets.** Раньше eval составлялся исключительно из событий, item которых был в train-only top-N каталоге. Теперь все оцениваемые по контексту будущие события попадают в validation/test, включая OOV в виде target 1; OOV считается промахом. В отчёте раздельно хранятся основной Recall/NDCG, conditional NDCG и фактическое покрытие train-каталога. Reward MAE/RMSE, напротив, считается только для наблюдавшихся in-vocabulary объектов.
3. **Уточнение unit test session-return.** В фикстуре были сразу два разных случая: последнее событие первого пользователя с неполным 24h горизонтом (**цензурируется**) и последнее событие второго пользователя, для которого полный глобальный горизонт **доступен** и отсутствие возврата учитывается. Проверка теперь явно различает оба случая; итоговый общий счётчик medium остаётся равным 1. Это повышение качества теста, а не исправление исходного статистического алгоритма.
4. **CI preflight / установка PyTorch.** Включены `python -m pip check`, `compileall` и CPU-only PyTorch wheel для runner без CUDA, чтобы уменьшить риск расходования диска и вычислительных минут на неподходящие зависимости.
5. **Регрессионные тесты.** Добавлены проверки OOV-знаменателя Recall/NDCG, GPT-2 position IDs и корректного исключения цензурированных наблюдений.

## Подтверждённые ограничения

- Это **статический аудит исходников**, а не успешный `pytest` или обученная модель. Для завершения технической проверки обязательно запустить manual synthetic smoke и прочитать лог, затем отдельный реальный Yambda pilot.
- Top-N train-only каталог и подвыборка пользователей ограничивают качество. Основной Recall/NDCG теперь учитывает OOV промахи, а сопоставление с официальными leaderboard не допустимо.
- Reward model обучена только на наблюдавшихся прослушиваниях; она может быть плохо калибрована на невыданных объектах и на сгенерированных состояниях. Несогласие двух reward-head лишь эвристический индикатор ошибки.
- У модели аудита отдельные train-пользователи, но общий замороженный энкодер, поэтому auditor не независим от базовых обученных представлений.
- RL использует гипотетическое предположение «рекомендованный трек добавлен как прослушанный»; это **не модель причинной реакции пользователя**.
- Простые baseline являются собственными упрощёнными реализациями, а не точным PCTM / GPTRec-RL / ROLeR. 
- Полноценная ретенция / удовлетворённость пользователей не наблюдаются контрфактически; статистика возвращения за 24 часа описательна и правосторонне цензурирована.
- Нет подтверждённых реальных запусков на нескольких seeds / cutoffs; статистические выводы о преимуществе RL до проведения исследования отсутствуют.

## Приёмочный протокол

1. На конкретном Git SHA запустить `Manual Task 2 smoke (CPU synthetic only)`. Подтвердить `pip check`, `compileall`, весь `pytest`, короткий fit GPT-2, reward-head, RL horizon 1/5, сформированные `experiment.json` и `REPORT.md`. Убедиться, что status = `synthetic_smoke_only`.
2. Только если smoke успешен, запустить ручной `Manual Yambda-50M RL research` с `users=64`, `vocab=2048`, `training=pilot`. Прочитать реальные логи, артефакты и `source-git-sha.txt`, проверить метрики и утечки.
3. Перед конкурсными заявлениями повторить хотя бы несколько seeds / временных срезов с фиксированным выбором гиперпараметров на validation и отдельным тестом. Приложить таблицы всех конфигураций, не только лучших.
4. При любых ошибках не выдавать код за завершённое исследование, а фиксировать их и исправлять с новым воспроизводимым запуском.

**Вывод аудита:** критичные методологические недочёты по позиции GPT-2 и OOV-оценке исправлены на уровне исходного кода. Сдача задания всё ещё блокируется отсутствием реально выполненных экспериментов и проверенного CI.
