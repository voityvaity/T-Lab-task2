## 1. Что было прочитано

### GPTRec-RL (Petrov & Macdonald, WWW 2024 workshop)
- Статья: https://arxiv.org/abs/2403.04875
- Официальный код: https://github.com/asash/gptrec_rl
- Реальные исходники: `recommenders/rl_generative/generative_tuning_recommender.py`, `pre_train_targets_builder.py`, `teacher.py`, `evaluation/configs/generative_rl/`.
- Их подход: GPTRec в схеме Next-K с teacher–student-предподготовкой и оптимизацией beyond-accuracy (разнообразие / популярность), а также сравнение с greedy reranking. В коде есть PPO, value function, KL, clipping и другие настройки.
- **У нас:** GPT2LMHeadModel с next-item CE, отдельная модель предсказания дослушивания, одно- и пятишаговый REINFORCE + KL, сравнение с reranking. Это **не точная реплика** GPTRec-RL, teacher–student и PPO не реализованы.
- **Контроль:** RL против фиксированного GPT-2 и против того же GPT-2 с reward reranking; отдельно измеряем экспозиционное смещение за пять шагов.

### ROLeR (Zhang et al., CIKM 2024)
- Статья: https://arxiv.org/abs/2407.13163
- Официальный код: https://github.com/ArronDZhang/ROLeR
- Основная идея: оценка reward подвержена ошибкам и отклонениям в новых пользовательских состояниях; для RL имеют значение reward shaping и учёт неопределённости.
- **У нас:** два независимо инициализированных reward-head на одном пуле обучающих пользователей; в `conservative` функция равна среднему их предсказаний минус половина абсолютного расхождения (то есть минимум этих двух прогнозов). Это **простая эвристика**, не воспроизведение ROLeR и не откалиброванная нижняя граница.
- Отдельный третий auditor head обучается на других TRAIN-пользователях, а не используется в градиенте RL. Все три head используют один замороженный GPT-2 encoder, значит нет независимости базового представления.
- **Контроль:** сравнить `completion` против `conservative`; считать расхождение с аудитором, среднее абсолютное несогласие head на выданных рекомендациях и NDCG. Если «улучшился» только оптимизированный предиктор, это подозрение на reward hacking, а не подтверждённое улучшение.

### Sequential Capacity Probes (Spotify Research, RecSys 2026)
- Официальный код: https://github.com/spotify-research/sequential-capacity-probes
- Конкретные реализации: `src/capacity_probes/models/seqrules.py` и `pctm.py`.
- Авторы показывают, что интерпретируемые статистические модели переходов иногда конкурентоспособнее сложных последовательных нейросетей.
- **У нас:** отдельный `SequentialRulesBaseline` из одноступенчатых переходов и popularity backoff; и `PopularityBaseline`. Обе модели используют только сохранённую обучающую подвыборку и общие тестовые истории.
- **ВАЖНО:** наш упрощённый одношаговый baseline **не есть** официальный PCTM / полная SeqRules. Не сравнивать наши численные метрики с опубликованными таблицами из-за других данных, split и определения задачи.
- Если GPT-2 отстаёт от такого простого контроля, нельзя интерпретировать высокий reward после RL как большой прогресс рекомендательной системы.

### Yambda (Yandex, 2025)
- Данные и документация: https://huggingface.co/datasets/yandex/yambda
- Yambda-50M: `listens.parquet`, timestamp = интервалы по пять секунд, процент дослушивания, длительность трека.
- Наш словарь строится из TRAIN и ограничен `vocab_size`. Validation/test-позитивы вне словаря фиксируются как непокрытые, а не превращаются в отрицательные примеры. **Ranking-метрики считаются условно по доступным целевым объектам**.
- Для честной финальной работы необходимо публиковать долю покрытия цели train-каталогом, количество пользователей и наблюдений, источниковую ревизию, временные границы и SHA-256 когорты.

## 2. Абляции и контроль интерпретации

| Вариант | Главное сравнение | Слабое место |
| --- | --- | --- |
| Popularity | статистический контроль | не учитывает историю |
| Sequential Rules (наш упрощённый) | простая последовательная модель против GPT-2 | только переход последнего token, trained on capped train examples |
| GPT-2 next-item | исходная релевантность | при свободной генерации история может быть вымышленной |
| GPT-2 + reward rerank | можно ли обойтись без изменения весов | reward оценивает ненаблюдавшиеся альтернативы |
| RL completion (1 шаг) | вырос ли предсказанный reward | model exploitation |
| RL completion (5 шагов) | влияние долгосрочного rollout | нет симулятора реакции пользователя |
| RL watch_time | цель в секундах против процента | предпочтение длинного контента |
| RL balanced | контролируем повтор / популярность | вручную установленные коэффициенты |
| RL conservative | штраф за разногласие двух reward-head | несогласие не является калиброванной неопределённостью |
| Разные KL | trade-off между наградой и релевантностью | сильный KL может свести RL к исходной модели |

Все методы получают одинаковые test targets, prequential-контексты и train-only каталог. RL-конфигурация выбирается **только на validation**, а test служит для окончательного описательного сравнения. Не подбирать победителя по test.

Измерять по каждому варианту: Recall@10, NDCG@10, среднюю прогнозируемую награду, оценку аудитора, disagreement, повторяемость, покрытие, долю самой частой top-1 рекомендации, среднюю популярность и длину треков, user-cluster bootstrap. Для пяти шагов дополнительно Jensen–Shannon divergence реальных и сгенерированных контекстов.

## 3. Наблюдаемый долгосрочный proxy

Из реальной хронологии тестового периода считаем: окончание сессии при перерыве **больше 30 минут**, факт возвращения в течение **24 часов** после окончания, отдельно для групп по дослушиванию. Поскольку события в Yambda измеряются 5-секундными bins, пороги: 360 и 17 280.

**Цензурирование:** в эту описательную статистику входят только session-end события, для которых в датасете существует весь последующий 24-часовой горизонт. Не использовать наблюдение, у которого последующая дата уже за концом исходных логов.

Наблюдаемая ассоциация предыдущего дослушивания и возвращения **не является причинным эффектом** рекомендации. Пассивные логи без известных показов и propensities не позволяют достоверно оценить retention новой политики. Для этого нужен онлайн A/B или специальный logging policy.

## 4. Что ещё не сделано

- **Не выполнены** реальный Yambda-fit, проверка численных метрик, многократные прогоны разных seeds / временных срезов.
- **Не реализованы** настоящий teacher–student GPTRec Next-K, полноценный PCTM, exact ROLeR, корректный off-policy evaluator и калиброванные контрфактические значения reward.
- До принятия конкурсной работы требуется запустить manual synthetic smoke, затем real Yambda pilot и расширенные исследования; сохранить артефакты и точные версии зависимостей; после проверки самостоятельно интерпретировать отрицательные и положительные результаты.

## 5. Вывод для будущего отчёта

Самое интересное открытое для **нашей** реализации сравнение: дают ли on-policy модельные rollouts хоть какой-то прирост помимо reranking, если жёстко ограничить падение NDCG и не игнорировать неопределённость RM. Успех RL не предполагается. Поведение может ухудшиться из-за сдвига между сгенерированными и наблюдавшимися действиями.
